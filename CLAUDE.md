# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Qt 6 (≥ 6.4) / C++17 desktop CW (Morse) trainer for a real straight key. Key input comes from a serial modem status line, a Linux GPIO line, or Space bar / on-screen button. See README.md for wiring and usage.

## Build & test

```bash
# Fedora deps: cmake gcc-c++ qt6-qtbase-devel qt6-qtmultimedia-devel
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure   # runs core_test
./build/core_test                            # same tests, direct
./build/morse-trainer
```

There is a single test executable (`tests/core_test.cpp`) using hand-rolled `CHECK`/`CHECK_EQ` macros and one `main()`; there is no per-test filtering. Only the `morsecore` library is unit-tested — the core test target does not link Qt, so it builds and runs fast.

## Architecture

Two layers, enforced by CMake:

- **`morsecore` (static lib, plain C++, no Qt)** — `morse.*` (table, prosigns as `<SK>`, PARIS/Farnsworth `timing()`, edit distance), `decoder.*` (adaptive straight-key decoder), `trainer.*` (Koch groups, alignment-based grading, accuracy stats). Keep Qt out of these files so `core_test` stays Qt-free.
- **App (Qt)** — key sources, audio, widgets, `MainWindow`.

### Key timing path (the core design concern)

Accurate edge timing is the point of the app, so timestamps are captured as close to hardware as possible and never taken when the GUI handles the event:

1. `KeySource` subclasses (`SerialKeySource`, `GpioKeySource`) run their own thread and emit `keyChanged(down, tUs)` with a `CLOCK_MONOTONIC` µs timestamp (`monotonicUs()` in `keysource.cpp`). Serial uses `TIOCMIWAIT` with a 1 kHz polling fallback; GPIO uses the GPIO uAPI v2 with kernel edge timestamps. No libgpiod/QSerialPort — kernel interfaces directly.
2. `MainWindow` connects with `Qt::QueuedConnection`; keyboard/button input is stamped with `monotonicUs()` in the event filter.
3. `MainWindow::setInput()` ORs all input sources (hardware/keyboard/button bitmask) and, only on a combined state change, drives the sidetone (`ToneGenerator::setKeyed`), the paper tape (`KeyScope::addEdge`) and the decoder.
4. `Decoder` is purely event-driven: `keyDown/keyUp/tick` each return emitted text (symbol, `" "`, or empty). A 5 ms `QTimer` calls `tick()` so characters/word spaces flush during silence. It adapts speed by clustering the last `kWindow` marks into dits/dahs and adapts word-gap threshold to recent inter-character gaps (Farnsworth-tolerant).

### Audio

`ToneGenerator::render()` produces both live sidetone and scheduled playback (`play(std::vector<morse::Segment>)`, generated by `morse::timing`) sample-accurately, reading the key state per sample. On Qt ≥ 6.11 it runs from `QAudioSink`'s real-time callback (`start(callback)`) on the audio thread; older Qt falls back to pull mode via `QIODevice::readData()`. Pull mode on Qt 6.11/PipeWire underruns with small buffers (it pulls ~85 ms chunks), so don't switch the default path back to it. Cross-thread parameters are `std::atomic`; the playback queue is mutex-guarded. Raised-cosine ramps avoid key clicks.

### Tests

`keyText()` in `core_test.cpp` simulates a human: it feeds `morse::timing()` output into a `Decoder` with optional jitter and ticks every 5 ms like the UI timer. Use it for new decoder tests.

Settings persist via `QSettings` to `~/.config/morse-trainer/morse-trainer.conf`.
